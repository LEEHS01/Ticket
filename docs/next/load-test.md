## 3. 해석

1. **요청마다 하는 처리(순번 확인·폴링·진입·이탈·1명 승격)는 인원에 거의 영향을 받지 않는다.** 1만 → 30만 명(30배)에서 중앙값이 20~40µs → 50~70µs로 2~3배. 쓰는 명령이 `ZRANK`·`ZSCORE`·`ZADD`·`ZREM`(O(log N))과 `ZCARD`(O(1))뿐이라 예상과 맞는다. 95%·최대값의 수백 µs는 반복 중 한두 번 튀는 값(같은 PC의 다른 작업·할당기)이다.
2. **인원에 비례해 커지는 처리가 하나 있었다: 폴링이 끊긴 대기자 정리.** `advance()`가 `ZRANGEBYSCORE seen -inf (지금-대기TTL)`로 끊긴 사람을 **전부** 가져와 하나씩 `ZREM` 했다. 끊긴 사람 수 S에 비례(30만 명 규모에서 1명당 약 5µs)하고, **30만 명이 한꺼번에 끊기면 Lua 한 번에 1.4초**였다. Lua가 도는 동안 Redis는 다른 요청을 받지 못하므로 그 1.4초 동안 **모든 회차의 대기열·선점·요청 제한이 멈춘다.** "한꺼번에 끊김"은 드물지 않다: 사용자들의 네트워크 문제, 프론트 배포, 그리고 1단계에서 넣은 **장애 유예가 끝나는 순간**(유예 동안 미뤄 둔 정리가 한 번에 몰림).
3. **고친 것(작게, 같은 구조 안에서):** 한 번의 상태 전진이 지우는 끊긴 대기자와 승격하는 인원을 각각 최대 500명으로 묶었다. 승격 후보 중 아직 못 지운 끊긴 대기자는 승격하지 않고 지운다. 상한 때문에 빈자리와 대기자가 함께 남을 수 있어 새 진입은 기다리는 사람이 없을 때만 바로 입장한다(새치기 방지). **결과: 30만 명이 모두 끊겨도 한 번에 3.7ms.** 남은 사람은 다음 요청들이 500명씩 이어서 지운다(30만 명이면 약 600번, Redis 시간 합계 약 2초를 여러 요청에 나눠 씀). 그 사이에는 이미 떠난 사람이 다른 사람의 "앞 인원"에 잠시 더해져 보인다. 통합 테스트 `QueueBoundedWorkIT`로 동작을 고정했다.
4. **승격 100명(입장자 전원 만료)이 1.2~1.4ms**: 입장 인원(`QUEUE_MAX_ACTIVE`)에 비례한다. 상한 500명이라 `QUEUE_MAX_ACTIVE`를 크게 잡아도 한 번에 약 6~7ms를 넘지 않는다(500명 기준 추정, 재지 않음).
5. **메모리**: 30만 명에 약 250~280MiB. 회차 여러 개에 동시에 수십만 명이 몰리면 Redis 메모리가 먼저 문제가 된다(관리형 Redis 크기 선택의 근거).

## 5. 요청량 테스트 — 예행

- 스크립트: `test/load/k6/queue_load.js`. 대상 주소·회차·대기자 단계(`WAITERS`)·단계 시간·예매자 수·폴링 간격을 매개변수로 받는다. 대기 트래픽이 0인 기준선을 먼저 돌린 뒤 대기자를 단계적으로 올리고, 그동안 예매자가 좌석 조회·선점·확정·취소를 반복해 `flow` 태그별 응답 시간(중앙값·95%·99%)과 오류율을 남긴다.
- **로컬 예행: 했다**(k6 v2.4.0, 사용자 확인 뒤 grafana/k6 공식 릴리스를 체크섬 확인 후 배포판 `~/bin/k6`에만 설치). 서버 1대, `QUEUE_MAX_ACTIVE=5`(줄이 생기게), 요청 제한은 테스트용으로 크게, 기준선 20초 → 대기자 20명 → 50명(각 30초) + 예매자 2명.
- **예행에서 스크립트 문제 2개를 찾아 고쳤다**: ① k6는 기본으로 반복마다 쿠키를 지워 두 번째 진입부터 `403 CSRF_INVALID`가 났다(`noCookiesReset: true`로 해결) ② 실패하면 빈 루프로 초당 약 1,900건을 두드렸다(실패 시 1초 쉬고, VU마다 처음 3개의 예상 밖 응답을 로그로 남기게 함). 서버 쪽 오류는 없었다(서버 로그 WARN/ERROR 0).
- 고친 뒤: 검사 5,316개 모두 통과, 예매·취소 619회, 실패 요청 0.04%(선점 경쟁의 `409 SEAT_TAKEN`, 검사에서는 정상으로 봄). 흐름별 응답 시간이 요약에 나오는 것을 확인했다(예: `book_confirm` 중앙값 25ms·95% 39ms, `queue_status` 중앙값 4ms). **이 수치는 스크립트가 동작한다는 확인일 뿐 결론이 아니다.**
- 예행으로 생긴 것: `ticketing_next` DB에 k6 가상 사용자 계정 165개와 예매 1,699건(모두 취소). 테스트 전용 DB라 남겨 두었다.
- 로컬 수치를 결론으로 쓰지 않는 이유: 부하 도구·서버·MySQL·Redis가 한 PC의 CPU를 나눠 쓰고 네트워크가 루프백이라, "무엇이 먼저 막히는가"가 운영과 다르게 나온다.

## 6. 대기열을 별도 서비스로 떼어 낼 필요가 있는가 (이 측정으로 말할 수 있는 범위)

- **알고리즘 면에서는 지금 구조로 충분하다.** 요청마다 하는 처리가 30만 명에서도 수십 µs이고, 유일하게 인원에 비례하던 처리는 고쳐서 한 번 3.7ms 이하로 묶였다. Redis 한 대가 단일 스레드로 처리할 수 있는 요청 수(대략 초당 수만 건, AWS에서 확인할 값)를 생각하면 대기열 Lua가 먼저 한계가 될 가능성은 낮다.
- **떼어 낼지 판단할 근거는 AWS 측정에 남아 있다.** ① 대기 폴링이 늘 때 같은 서버(파드)의 예매 API 응답 시간이 나빠지는가(서버 CPU·스레드·DB 연결 공유) ② 한 Redis를 대기열·선점·요청 제한이 함께 쓸 때 서로 간섭하는가 ③ 대기자 수십만 명의 폴링(초당 수만 건)에서 세션 조회(MySQL SELECT, 2.4절)가 DB 부하가 되는가. 특히 ③은 1단계에서 세션을 DB로 옮긴 대가라, 대기 폴링만 세션 확인을 가볍게 하는 방법(예: 대기 토큰만으로 상태 조회)이 분리보다 먼저 검토할 대안이다.
- 정리: **"지금 당장 분리할 근거는 없다. 분리 여부는 AWS에서 ①~③을 재고 정한다."**

## 7. AWS 측정 계획 (지금은 하지 않음)

| 무엇을 | 조건 | 지표 |
|---|---|---|
| 기준선 | 예매자 VU 2~10, 대기 0 | 예매 API(좌석 조회·선점·확정) 응답 시간 중앙값·95%·99%, 오류율 |
| 대기 트래픽 영향 | 같은 예매자 + 대기 VU 단계적(예: 1천→5천→2만, 폴링은 서버 권장 간격) | 위 지표의 변화, 파드 CPU·스레드, Hikari 연결 대기, Redis CPU·명령 지연, RDS CPU·커넥션 |
| 오토스케일링 반응 | HPA 켬, 대기 VU를 급히 올림 | 새 파드가 뜨는 시간 동안의 오류율·지연, 파드 수 변화 |
| 관리형 Redis·DB | ElastiCache(클러스터 모드 끔)·RDS | Redis 메모리(대기자 수 × 약 1KB), 장애 조치 때 대기열 유지(1단계의 장애 유예 동작) |
| 부하 도구 | k6를 대상과 다른 인스턴스에서, 필요하면 여러 대 | 도구 CPU가 먼저 포화되면 그 지점 이상은 "측정 못 함"으로 적는다 |

준비할 것: 요청 제한을 테스트 전용 값으로 올린 설정, 가상 사용자 계정을 미리 만드는 단계(지금 스크립트는 VU마다 가입), 테스트 전용 DB·Redis.

## 8. 한계와 측정하지 못한 것

- 서버 1대·로컬 루프백·curl 측정이라 API 응답 시간의 절대값은 의미가 작다(프로세스 시작 비용 포함). 서버 2대 조건, CPU 제한(taskset·cgroup) 조건은 이번 범위(데이터 규모)에서 돌리지 않았다.
- 끊긴 대기자 정리는 파괴적이라 규모마다 1번씩만 쟀다(반복 없음).
