## 3. 해석

1. **요청마다 하는 처리(순번 확인·폴링·진입·이탈·1명 승격)는 인원에 거의 영향을 받지 않는다.** 1만 → 30만 명(30배)에서 중앙값이 20~40µs → 50~70µs로 2~3배. 쓰는 명령이 `ZRANK`·`ZSCORE`·`ZADD`·`ZREM`(O(log N))과 `ZCARD`(O(1))뿐이라 예상과 맞는다. 95%·최대값의 수백 µs는 반복 중 한두 번 튀는 값(같은 PC의 다른 작업·할당기)이다.
2. **인원에 비례해 커지는 처리가 하나 있었다: 폴링이 끊긴 대기자 정리.** `advance()`가 `ZRANGEBYSCORE seen -inf (지금-대기TTL)`로 끊긴 사람을 **전부** 가져와 하나씩 `ZREM` 했다. 끊긴 사람 수 S에 비례(30만 명 규모에서 1명당 약 5µs)하고, **30만 명이 한꺼번에 끊기면 Lua 한 번에 1.4초**였다. Lua가 도는 동안 Redis는 다른 요청을 받지 못하므로 그 1.4초 동안 **모든 회차의 대기열·선점·요청 제한이 멈춘다.** "한꺼번에 끊김"은 드물지 않다: 사용자들의 네트워크 문제, 프론트 배포, 그리고 1단계에서 넣은 **장애 유예가 끝나는 순간**(유예 동안 미뤄 둔 정리가 한 번에 몰림).
3. **고친 것(작게, 같은 구조 안에서):** 한 번의 상태 전진이 지우는 끊긴 대기자와 승격하는 인원을 각각 최대 500명으로 묶었다. 승격 후보 중 아직 못 지운 끊긴 대기자는 승격하지 않고 지운다. 상한 때문에 빈자리와 대기자가 함께 남을 수 있어 새 진입은 기다리는 사람이 없을 때만 바로 입장한다(새치기 방지). **결과: 30만 명이 모두 끊겨도 한 번에 3.7ms.** 남은 사람은 다음 요청들이 500명씩 이어서 지운다(30만 명이면 약 600번의 요청에 나눠 지운다). 그 사이에는 이미 떠난 사람이 다른 사람의 "앞 인원"에 잠시 더해져 보인다. 통합 테스트 `QueueBoundedWorkIT`로 동작을 고정했다.
4. **승격 100명(입장자 전원 만료)이 1.2~1.4ms**: 입장 인원(`QUEUE_MAX_ACTIVE`)에 비례한다. 한 번에 승격하는 인원은 최대 500명으로 묶여 있다(500명일 때의 시간은 재지 않았다).
5. **메모리**: 30만 명에 약 250~280MiB. 관리형 Redis 크기를 고를 때 이 값(대기자 1명당 측정값)을 쓴다.

## 6. 대기열을 별도 서비스로 떼어 낼 필요가 있는가

### 6.1 이 측정으로 말할 수 있는 것(알고리즘이 인원에 따라 어떻게 변하는가)

- 요청마다 하는 처리(순번 확인·폴링·진입·이탈·1명 승격)는 대기자 1만 → 30만 명에서 2~3배만 늘었다(O(log N)). 30만 명에서도 한 번 수십 µs다.
- 인원에 비례하던 유일한 처리(끊긴 대기자 일괄 정리, 30만 명에서 1.4초)는 같은 구조 안에서 고쳐 한 번 3.7ms 이하로 묶였다. 승격도 한 번 500명 상한이다.
- 대기 상태 조회 API의 응답 시간은 대기자 수와 거의 무관했다(1만·30만 명 모두 중앙값 7ms 안팎, 서버 1대·로컬).
- 따라서 **대기자 수가 늘어서 대기열 알고리즘이 먼저 막히는 일은 이 측정 범위(30만 명)에서는 없다.** 이것만으로는 분리할 근거가 없다.

### 6.2 이 측정으로는 말할 수 없는 것(AWS에서 확인)

- 대기 폴링 요청 수가 늘 때 **같은 파드에서 도는 예매 API**가 느려지는가(파드 CPU·스레드·DB 연결을 나눠 씀).
- 한 Redis를 대기열·선점·멱등키·요청 제한이 함께 쓸 때, Redis 단일 스레드의 처리량 한계와 서로의 지연.
- 대기 폴링마다 하는 **세션 조회(MySQL SELECT 1번)**가 DB 부하·연결 수의 병목이 되는가(1단계에서 세션을 DB로 옮긴 대가). 이것이 문제가 되면 분리보다 먼저 "대기 상태 조회는 대기열 토큰만으로 확인" 같은 경량화를 검토한다.
- 오토스케일링 반응, 관리형 Redis 자동 전환 중의 동작.
- 결론: **지금 분리할 근거는 없다. 분리 여부는 7장의 AWS 측정 ①~③ 결과로 정한다.**

| ⑥ | Redis 자체 | 엔진 CPU, 명령 지연, 메모리(대기자 수에 따른 증가), 느린 명령 기록(SLOWLOG) |

### 7.2 조건

- 서버 수: 파드 고정 수(예: 1개, 2개, 4개처럼 몇 단계)로 각각 ①②를 재고, 그다음 HPA를 켜고 ④를 잰다. 단계의 실제 값은 AWS 단계에서 정한다.
- 자원: 파드의 CPU·메모리 요청과 제한을 k8s 설정 그대로 두고 측정 조건에 적는다(JVM 힙 비율, `DB_POOL_SIZE`, `QUEUE_MAX_ACTIVE`도 함께 기록).
- 부하를 내는 위치: 대상 클러스터와 **다른** 인스턴스(같은 리전, 같은 VPC 또는 공개 주소 중 무엇을 쓰는지 기록). 부하 도구의 CPU·네트워크도 함께 기록하고, 도구가 먼저 포화되면 그 이상은 "측정 못 함"으로 적는다. 필요하면 도구 인스턴스를 늘린다.
- 요청 제한: 테스트 전용 설정으로 한도를 올리고, ALB·WAF 제한은 예외 처리하거나 포함 여부를 먼저 정한다(`test/load/README.md` 3장).
- 데이터: 테스트 전용 DB·Redis, 계정은 `prepare_accounts.sh`로 미리 만든 파일(VU 수 이상). 회차는 좌석이 넉넉한 것.
- 관리형 Redis는 클러스터 모드를 끈다(Lua가 여러 키를 함께 다룬다).

### 7.3 통과 기준을 잡는 방법

- 숫자는 미리 정하지 않는다. 먼저 ②의 기준선(대기 0)에서 예매 API의 95%·99%를 재고, **"대기 트래픽이 올라가도 예매 95%·99%가 기준선 대비 얼마 이상 나빠지지 않는다"**와 **"오류율(5xx)이 얼마 이하"**를 그 결과를 보고 사용자와 정한다.
- ⑤는 "중복 판매 0, 전환 뒤 서버 재시작 없이 회복, 대기자가 줄에 남음"을 필수 조건으로 둔다(1단계에서 로컬로 확인한 동작이 관리형 Redis에서도 같은지).
- 각 단계는 같은 조건으로 두 번 이상 재고, 두 번의 차이도 함께 적는다.

### 7.4 데이터 규모 테스트에서 미리 보이는 병목 후보

- **Redis 단일 스레드 공유**: 대기열·선점·멱등키·요청 제한이 모두 한 Redis로 간다. 요청 하나가 Redis를 2~4번 부른다(요청 제한 1, 토큰 확인 1, 폴링 Lua 1 등). 대기 폴링이 늘면 Redis 명령 수가 그 배수로 는다.
- **세션 조회의 MySQL 부하**: 로그인한 요청(대기 폴링 포함)마다 SELECT 1번(1단계). 대기 폴링 수만큼 DB 조회가 늘고, 파드의 DB 연결 풀을 예매 트랜잭션과 나눠 쓴다.
- **승격 몰림**: 입장자가 한꺼번에 만료되면 한 번의 상태 전진이 최대 500명을 승격한다(이번 측정에서 100명에 1.2~1.4ms). `QUEUE_MAX_ACTIVE`를 크게 잡을 때 확인한다.
- **끊긴 대기자 정리의 지연**: 고친 뒤에는 한 번 500명씩 나눠 지우므로 Redis는 멈추지 않지만, 대량으로 끊긴 직후에는 "앞 인원"이 실제보다 크게 보이는 시간이 생긴다.
- **Redis 메모리**: 대기자 1명당 약 0.8~1.6KB(측정값). 회차 여러 개에 동시에 많은 대기자가 몰릴 때의 메모리를 ⑥에서 본다.

## 8. 한계와 측정하지 못한 것

- 서버 1대·로컬 루프백·curl 측정이라 API 응답 시간의 절대값은 의미가 작다(프로세스 시작 비용 포함). 서버 2대 조건, CPU 제한(taskset·cgroup) 조건은 이번 범위(데이터 규모)에서 돌리지 않았다.
- 끊긴 대기자 정리는 파괴적이라 규모마다 1번씩만 쟀다(반복 없음).
- 100만 명 이상은 재지 않았다.
- 요청량은 예행(5장)만 했다. 대기자 수천~수만 명의 폴링은 이 PC에서 만들지 않았다.
- 측정 뒤 정리: 전용 Redis 두 개는 측정이 끝나면 끄고(데이터 없음), 결과 파일은 `/mnt/d/tkn-load/`(약 200KB)에 남겼다. API 측정용으로 가입한 계정 12개(`probe-…@example.com`, 30만 명 첫 시도가 스크립트 오류로 중단된 몫 포함)가 `ticketing_next` DB에 남아 있다.
