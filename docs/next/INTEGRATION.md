# 통합 검증 기록 (2026-11-24)

조율 세션이 새 화면(`frontend/`)과 백엔드 v4(`backend/`)를 컨테이너로 묶어 직접 확인한 내용이다.
각 세션이 스스로 확인했다고 보고한 것은 여기에 적지 않았다. 여기 있는 것은 모두 이 환경에서 다시 실행해 본 것이다.

## 환경

| 항목 | 값 |
|---|---|
| 위치 | WSL 배포판 `ticketing`의 Docker 엔진 (Docker Desktop과 예전 배포판은 꺼 둠) |
| 실행 | `compose.yaml` 그대로, 프로젝트 이름 `tkn-next`, 이미지 태그 `next` |
| 구성 | frontend 1, backend 2, MySQL 8.4, Redis 7, migrate(끝나면 종료) |
| 접속 | `http://localhost:8088` (이 PC에서만) |
| 커밋 | `next` 브랜치 50ecba8 시점 |

실행 방법(WSL 배포판 `ticketing` 안에서, 저장소 루트에 `.env`가 있어야 한다):

```bash
cd /mnt/d/ticketing-next
export APP_VERSION=next COMPOSE_BAKE=false
docker compose --project-name tkn-next build
docker compose --project-name tkn-next up -d --wait
```

`COMPOSE_BAKE=false`를 준 이유: 이 배포판에서 기본 빌드 방식(bake)이 시작 직후 멈춰 진행되지 않았다. 원인은 확인하지 않았다.

## 확인한 것

### API (v4)
- 공연 18개, `tagline`·`region`·`createdAt`, 상세의 `venueInfo`, `region` 필터
- 배너 6개(공연 15, 4, 1, 6, 8, 12 순), 공지 6건(고정 공지가 맨 앞), 공지 상세, 없는 공지 404, `page=0`은 400, 마지막 쪽을 넘기면 빈 목록
- 랭킹: 일간·주간·전체의 순위가 서로 다름, 점유율 합 100.1~100.2, 잘못된 기간 400
- 좌석 배치 미리보기: 토큰 없이 200, 좌석 항목은 `row`·`number`·`grade`뿐이고 판매·선점 상태가 없음
- 비로그인으로 좌석 조회 401

### 예매 흐름
- 가입 → 대기열 진입 → 좌석 2석 선점 → 다른 사용자의 같은 좌석 선점 409 → 잘못된 결제 수단 400 → 간편결제로 확정 → 같은 멱등키 재요청은 같은 예매 → 내 예매에 결제 수단 표시 → 다른 사용자는 조회·취소 불가(404) → 취소 → 로그아웃 뒤 401

### Redis를 통째로 비웠을 때 (다른 클라우드로 넘어간 상황과 같음)
- 로그인 유지, 내 예매 조회 정상
- 선점 중이던 사용자의 확정은 `409 HOLD_EXPIRED`
- 대기 중이던 사용자의 상태 조회는 `401 QUEUE_TOKEN_INVALID`, 다시 진입 가능
- 풀린 좌석을 다른 사용자가 선점·확정, 그 뒤 원래 사용자가 같은 좌석을 잡으려 하면 `409 SEAT_TAKEN` (판매 1건)

### Redis를 멈췄을 때
- 공연 목록·상세·배너·랭킹·공지 200, 로그인 상태 확인 200, 내 예매 조회 200, 새 가입 가능, 예매 취소 가능
- 대기열 진입·좌석 조회·대기 상태 조회는 `503 SERVICE_UNAVAILABLE`, `Retry-After: 5`, 한국어 안내 문구
- 백엔드 컨테이너 2개 모두 healthy 유지(트래픽에서 빠지지 않음)
- 둘러보기 응답 시간: Redis 정상 중앙값 45ms, 정지 중 48ms, 복구 뒤 45ms (30회씩, `127.0.0.1` 기준)
- Redis를 다시 켜면 백엔드를 재시작하지 않아도 대기열 진입이 바로 200

### 화면 (브라우저, 실제 백엔드)
- 1440px: 메인(배너 대체 표시, 공지 띠, 티켓 오픈 예정, 랭킹, 전체 목록), 상세(오른쪽 예매 상자, 달력, 회차, 등급별 잔여), 비로그인 예매 → 로그인 → 가입 → 고르던 회차로 복귀, 좌석 선택, 예매 확인·모의 결제, 완료, 내 예매, 랭킹, 검색, 공지, 티켓 오픈
- 375px: 메인, 상세. 가로 넘침 없음
- 콘솔 오류 없음

### 이미지 반영 뒤 (2026-11-25, 커밋 6bba0fa)
- 메인 배너 6장을 PC 1440px에서 한 장씩 넘겨 확인: 제목·부제·기간이 모두 읽힌다. 왼쪽이 밝은 `banner-6`(구름 정거장)도 글자 뒤의 어두운 처리로 읽힌다
- 안내 그림: 없는 페이지, 검색 결과 없음에서 표시됨
- 모바일 375px 메인: 배너 카드와 하단 탭 정상
- 발견한 문제: 메인 배너 영역(`.hero`)이 `overflow: hidden`이라 안쪽 요소에 `scrollIntoView`가 걸리면 가로로 스크롤되어 슬라이드가 밀려 보인다. UI 세션에 수정을 맡겼다

## 확인하지 못한 것
- 모바일 폭에서의 예매 전체 흐름(메인과 상세만 봄)
- 대기 화면(동시 입장 한도를 낮춰 실제로 기다리는 상황)
- Redis가 멈춘 상태에서의 화면 동작(API로만 확인)
- 대기 화면의 안내 그림(대기 상태를 만들지 않아 보지 못함)
- 백엔드 단위·통합 테스트를 조율 세션이 다시 돌리지는 않음(백엔드 세션 보고: 단위 94, 통합 36 통과)

## 알아둘 점
- WSL 배포판은 연결된 터미널이 없으면 잠시 뒤 스스로 꺼지고, 그때 컨테이너도 함께 멈춘다(재시작 설정이 없다). 화면이 열리지 않으면 위 실행 방법의 `up -d --wait`를 다시 실행하고 그 터미널을 열어 둔다. 데이터는 볼륨에 남아 있다.
- 이 PC에서 `http://localhost:8088`은 연결마다 IPv6를 먼저 시도해 지연이 생긴다(compose가 `127.0.0.1`에만 포트를 연다). 측정이나 스크립트에는 `http://127.0.0.1:8088`을 쓴다. 브라우저로 볼 때는 큰 차이가 없다.
- WSL 안에서는 이 작업 폴더의 git 명령이 동작하지 않는다(worktree의 git 경로가 Windows 형식). git은 Windows 쪽에서 쓴다.
