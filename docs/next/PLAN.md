# 미리내 마당 업그레이드 계획 (next)

과제 제출본(`main`, 태그 `v2.0-base`·`v3.0-improved`)은 그대로 두고, 이 브랜치(`next`)에서 제품을 다시 끌어올린다.
조율 세션이 이 문서를 관리한다. 각 작업 세션은 이 문서를 먼저 읽고, 바꿔야 할 것이 있으면 조율 세션에 알린다.

## 1. 목표

1. 화면을 실제 예매 서비스 수준으로 끌어올린다. 지금 화면은 기능은 되지만 "시제품"으로 보인다.
2. Redis를 포함해 **공유 캐시를 쓰지 않는다.** 서버 사이에 공유되는 상태는 전부 MySQL에 둔다.
3. 나중에 멀티 클라우드 DR(재해 복구) 구성으로 올린다. 그래서 "복제해야 할 상태 저장소는 DB 하나"가 되어야 한다.

## 2. 지켜야 할 것

### 2.1 공유 캐시 없음

| 지금 Redis가 하는 일 | 바꿀 방식 (MySQL) |
|---|---|
| 로그인 세션 (Spring Session Redis) | DB 세션 (Spring Session JDBC). 3장 참고 |
| 좌석 임시 선점 (키 TTL) | `seats`에 선점 정보 열(선점 식별자, 선점한 사용자, 만료 시각). "비어 있거나 선점이 만료된 좌석"만 잡는 조건부 `UPDATE` 한 번으로 전부 아니면 전무. 만료는 조회·선점 시점에 판단하고 별도 정리 작업에 의존하지 않는다 |
| 접속 대기열 (ZSET + Lua) | 대기열 테이블(자동 증가 번호 = 줄 선 순서). 입장 처리는 회차별 한 행을 잠근 트랜잭션 안에서 "만료된 입장자 정리 → 빈자리만큼 앞번호부터 승격" |
| 멱등키 | 유니크 키를 가진 테이블. 처리 중·완료 상태와 응답 보관 |
| 로그인 실패 잠금 | `users`의 실패 횟수·잠금 해제 시각 열 |
| 요청 제한 | 서버 한 대 안에서만 세는 메모리 카운터(공유 상태 아님). 전체 한도는 운영에서 로드밸런서·WAF가 맡는다는 점을 문서에 적는다 |

- 서버 메모리에 사용자 상태를 두지 않는 원칙은 그대로다(요청 제한 카운터만 예외이고, 잃어도 되는 값이다).
- 스케줄러가 꼭 돌아야 정합성이 지켜지는 설계는 피한다. 정리 작업은 "돌면 좋고 안 돌아도 틀리지 않게" 만든다.
- `/readyz`는 MySQL만 확인한다. compose와 k8s에서 Redis를 뺀다.
- DB 부하가 늘어나는 지점(세션 조회, 대기열 폴링, 좌석 폴링)은 인덱스와 쿼리 수를 설계에 적고, 폴링 간격으로 조절한다.

### 2.2 실제 서비스 참고 범위

- 참고하는 것: 화면 종류와 흐름, 정보 배치 방식(영역 순서, 격자 열 수, 카드에 들어가는 정보), 치수와 밀도(배너 비율, 포스터 비율, 글자 크기 단계), 상호작용 방식.
- 가져오지 않는 것: 로고·서비스 이름·브랜드 색 조합, 이미지, 문구, 실제 공연·출연진 이름, 소스 코드.
- 결과물은 "국내 예매 서비스의 일반적인 구성을 따른, 이름과 색과 그림이 다른 서비스"여야 한다. 특정 사이트와 나란히 놓았을 때 같은 서비스로 보이면 안 된다.
- 다른 서비스 화면 캡처는 `.ref/`에만 둔다(git 제외). 저장소와 문서에 넣지 않는다.
- 공개 화면만 본다. 로그인, 예매 시도, 좌석 클릭, 자동 반복 요청, 내부 API 재호출은 하지 않는다.

### 2.3 이미지

- 이미지는 사용자가 생성 도구로 만들어 온다. 필요한 이미지는 "용도, 크기(px), 비율, 장수, 내용, 금지 사항"을 표로 정리하고 생성용 프롬프트를 붙인다.
- 이미지가 오기 전에도 화면이 깨지지 않게 대체 표시를 둔다.

## 3. 로그인 세션

기본안은 **DB 세션**이다(사용자 선호). 다른 안과의 비교는 조율 세션이 사용자에게 설명했고, 바뀌면 이 절을 고친다.

- Spring Session JDBC. 세션 쿠키는 지금과 같다(`HttpOnly`, `SameSite=Lax`, 운영 `Secure`).
- 세션 테이블 쓰기를 줄인다: 값이 바뀔 때만 저장하고, 마지막 접근 시각 갱신은 일정 간격(예: 1분)보다 촘촘하지 않게 한다.
- 만료 세션 삭제는 여러 서버가 동시에 돌려도 문제없는 방식으로 한다.
- 인증 확인 로직은 한 곳(필터 또는 서비스)에 모아, 나중에 토큰 방식으로 바꾸더라도 컨트롤러를 고치지 않게 한다.

## 4. 작업 나누기

| 세션 | 맡는 폴더 | 단계 |
|---|---|---|
| 조율 | `docs/next/`, `docs/ARCHITECTURE.md`, `compose.yaml` 조정 | 설계, 계약, 통합 검증 |
| 벤치마크 | `docs/next/benchmark/`, `.ref/` | 실제 서비스 분석, 화면 설계안, 이미지 목록 |
| 백엔드 | `backend/` (필요하면 `compose.yaml`의 backend·migrate·redis 부분, `k8s/`는 건드리지 않음) | ① Redis 제거(API 계약은 v3 그대로) → ② 새 화면에 필요한 API 추가 |
| UI | `frontend/` | 벤치마크 결과로 화면 전면 재구성 |

순서: 벤치마크와 백엔드 ①을 동시에 시작한다. 벤치마크가 끝나면 조율 세션이 계약 v4를 정하고 UI와 백엔드 ②를 시작한다.

## 5. 공통 규칙

- 작업 폴더는 `D:\ticketing-next`(git worktree, 브랜치 `next`)다. `C:\Users\이현수\Desktop\Docker\ticketing`(브랜치 `main`, 과제 제출본과 발표 자료)은 **읽기만** 한다.
- 커밋은 `next` 브랜치에만, 자기 폴더의 변경만, 의미 단위로 한다. push, 브랜치 전환, 태그, `main` 변경은 하지 않는다.
- AWS, Notion, Docker Hub는 건드리지 않는다. `kubectl`, `aws` 명령을 실행하지 않는다.
- C 드라이브 여유가 약 5GB다. 큰 파일과 빌드 산출물은 D 드라이브에 둔다.
- Docker Desktop과 예전 WSL 배포판(`Ubuntu-24.04`)은 꺼져 있고, 켜지 않는다(네트워크를 공유해 포트가 겹친다). 실행·검증 환경이 필요하면 D 드라이브의 WSL 배포판 `ticketing`(`wsl -d ticketing`, 저장소는 `/mnt/d/ticketing-next`)에 무엇이 설치돼 있는지 먼저 확인하고 그 안에서 한다. 새로 설치가 필요하면 무엇을 왜 설치하는지 보고한 뒤 진행한다.
- 사용자 결정이 필요한 일이 생기면 멈추지 말고, 기본값으로 진행하면서 "결정 필요" 항목으로 보고한다. 되돌리기 어려운 일(삭제, 외부 전송)만 먼저 묻는다.
- 검증하지 못한 것은 못 했다고 적는다.
