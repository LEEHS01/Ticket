# 미리내 마당 업그레이드 계획 (next)

과제 제출본(`main`, 태그 `v2.0-base`·`v3.0-improved`)은 그대로 두고, 이 브랜치(`next`)에서 제품을 다시 끌어올린다.
조율 세션이 이 문서를 관리한다. 각 작업 세션은 이 문서를 먼저 읽고, 바꿔야 할 것이 있으면 조율 세션에 알린다.

## 1. 목표

1. 화면을 실제 예매 서비스 수준으로 끌어올린다. 지금 화면은 기능은 되지만 "시제품"으로 보인다.
2. 상태를 **"잃으면 안 되는 것"과 "잃어도 되는 것"**으로 나눈다. 잃으면 안 되는 것은 MySQL에, 잃어도 되는 것은 Redis에 둔다(2.1).
3. 나중에 멀티 클라우드 DR(재해 복구) 구성으로 올린다. 클라우드 사이에 복제하는 저장소는 DB 하나이고, Redis는 클라우드마다 따로 두며 복제하지 않는다. 다른 클라우드로 넘어가면 Redis는 빈 상태로 시작한다.

> 2026-11-24 변경: 처음에는 "공유 캐시 없음, 전부 MySQL"로 정했으나, 사용자가 "장애 전환 때 대기열이 사라져 다시 줄을 서는 것이 일반적인 방식이라면 캐시를 쓰자"고 결정했다. 로그인 세션만 DB로 옮기고 나머지는 Redis에 둔다.

## 2. 지켜야 할 것

### 2.1 상태를 어디에 두는가

| 상태 | 저장소 | 장애 전환(다른 클라우드로 넘어감) 때 |
|---|---|---|
| 회원, 공연, 회차, 좌석 판매 여부, 예매 | MySQL (클라우드 사이 복제) | 유지된다. 기준 데이터 |
| **로그인 세션** | **MySQL** (Spring Session JDBC, 3장) | 유지된다(복제 지연만큼의 최근 로그인은 다시 로그인) |
| **로그인 실패 잠금** | **MySQL** (`users`의 실패 횟수·잠금 해제 시각 열) | 유지된다. 보안 상태라 장애 전환으로 초기화되면 안 된다 |
| 접속 대기열 | Redis (클라우드마다 따로, 복제 안 함) | **사라진다.** 사용자는 다시 줄을 선다 |
| 좌석 임시 선점 | Redis | **사라진다.** 고르던 좌석이 풀리고 다시 고른다. 판매된 좌석은 DB에 있어 영향 없다 |
| 멱등키 | Redis | 사라진다. 선점이 함께 사라지므로 재시도는 `HOLD_EXPIRED`가 되고 중복 예매는 생기지 않는다 |
| 요청 제한 | Redis | 사라진다(한도가 초기화될 뿐) |

- **Redis는 언제든 비어 있을 수 있다는 전제로 만든다.** Redis가 통째로 비워져도(장애 전환, 재시작) 중복 판매가 없어야 하고, 사용자는 "다시 줄 서기, 다시 좌석 고르기"만 하면 되어야 하며, 로그인은 유지되어야 한다. 이것을 테스트로 증명한다.
- **Redis가 죽어 있어도 둘러보기와 로그인은 동작해야 한다.** 공연 목록·상세, 로그인·가입·내 예매 조회·취소는 Redis 없이 된다. 예매 진행(대기열, 좌석, 선점, 확정)만 "잠시 후 다시 시도" 응답을 준다. `/readyz`는 MySQL 기준으로 판단하고, Redis 상태는 별도로 알 수 있게 한다.
- 중복 판매의 최종 방어선은 지금처럼 DB다(`WHERE status='AVAILABLE'` 영향 행 수 확인).
- 서버 메모리에 사용자 상태를 두지 않는 원칙은 그대로다.

### 2.2 실제 서비스 참고 범위

- 참고하는 것: 화면 종류와 흐름, 정보 배치 방식(영역 순서, 격자 열 수, 카드에 들어가는 정보), 치수와 밀도(배너 비율, 포스터 비율, 글자 크기 단계), 상호작용 방식.
- 가져오지 않는 것: 로고·서비스 이름·브랜드 색 조합, 이미지, 문구, 실제 공연·출연진 이름, 소스 코드.
- 결과물은 "국내 예매 서비스의 일반적인 구성을 따른, 이름과 색과 그림이 다른 서비스"여야 한다. 특정 사이트와 나란히 놓았을 때 같은 서비스로 보이면 안 된다.
- 다른 서비스 화면 캡처는 `.ref/`에만 둔다(git 제외). 저장소와 문서에 넣지 않는다.
- 공개 화면만 본다. 로그인, 예매 시도, 좌석 클릭, 자동 반복 요청, 내부 API 재호출은 하지 않는다.

### 2.3 이미지

- 이미지는 사용자가 생성 도구로 만들어 온다. 필요한 이미지는 "용도, 크기(px), 비율, 장수, 내용, 금지 사항"을 표로 정리하고 생성용 프롬프트를 붙인다.
- 이미지가 오기 전에도 화면이 깨지지 않게 대체 표시를 둔다.

## 3. 로그인 세션

**DB 세션**으로 한다(사용자 결정). 장애 전환 뒤에도 로그인이 유지되게 하려는 것이다.

- Spring Session JDBC. 세션 쿠키는 지금과 같다(`HttpOnly`, `SameSite=Lax`, 운영 `Secure`).
- 세션 테이블 쓰기를 줄인다: 값이 바뀔 때만 저장하고, 마지막 접근 시각 갱신은 일정 간격(예: 1분)보다 촘촘하지 않게 한다.
- 만료 세션 삭제는 여러 서버가 동시에 돌려도 문제없는 방식으로 한다.
- 인증 확인 로직은 한 곳(필터 또는 서비스)에 모아, 나중에 토큰 방식으로 바꾸더라도 컨트롤러를 고치지 않게 한다.

## 4. 작업 나누기

| 세션 | 맡는 폴더 | 단계 |

## 5. 공통 규칙

- 작업 폴더는 `D:\ticketing-next`(git worktree, 브랜치 `next`)다. `C:\Users\이현수\Desktop\Docker\ticketing`(브랜치 `main`, 과제 제출본과 발표 자료)은 **읽기만** 한다.
- 커밋은 `next` 브랜치에만, 자기 폴더의 변경만, 의미 단위로 한다. push, 브랜치 전환, 태그, `main` 변경은 하지 않는다.
- AWS, Notion, Docker Hub는 건드리지 않는다. `kubectl`, `aws` 명령을 실행하지 않는다.
- C 드라이브 여유가 약 5GB다. 큰 파일과 빌드 산출물은 D 드라이브에 둔다. 용량이 모자라면 다시 만들 수 있는 것(자기가 만든 빌드 산출물, npm·Maven 캐시, 임시 파일)은 지워도 된다. 그 밖의 파일(사용자 문서, 다운로드, 다른 프로젝트, WSL 디스크, Docker 데이터)은 지우지 말고 조율 세션에 알린다.
- Docker Desktop과 예전 WSL 배포판(`Ubuntu-24.04`)은 꺼져 있고, 켜지 않는다(네트워크를 공유해 포트가 겹친다). 실행·검증 환경이 필요하면 D 드라이브의 WSL 배포판 `ticketing`(`wsl -d ticketing`, 저장소는 `/mnt/d/ticketing-next`)에 무엇이 설치돼 있는지 먼저 확인하고 그 안에서 한다. 새로 설치가 필요하면 무엇을 왜 설치하는지 보고한 뒤 진행한다.
- 사용자 결정이 필요한 일이 생기면 멈추지 말고, 기본값으로 진행하면서 "결정 필요" 항목으로 보고한다. 되돌리기 어려운 일(삭제, 외부 전송)만 먼저 묻는다.
- 검증하지 못한 것은 못 했다고 적는다.

## 6. 대기열 부하 테스트 (2026-11-24 추가, 같은 날 범위 조정)

목적은 "대기열을 백엔드 안에 두고 Redis로 관리하는 지금 구조가 어디까지 버티는가"와 "대기 트래픽이 예매 API를 방해하는가"를 수치로 보는 것이다. 결과는 대기열을 별도 서비스로 떼어 낼지의 근거가 된다.

실제 인프라는 AWS에 올라간다. 로컬 PC의 요청량 수치는 운영 환경과 다르므로, 로컬에서는 환경과 무관하게 유효한 것만 재고 나머지는 AWS 단계로 넘긴다(사용자 결정).

| 구분 | 어디서 | 내용 |
|---|---|---|
| 데이터 규모 테스트 | **로컬(이번에 한다)** | 대기자를 Redis에 직접 채워 넣고(1만, 5만, 10만, 30만) 순번 확인·승격·이탈·폴링 끊긴 대기자 정리·새 진입 한 번의 시간이 인원에 따라 어떻게 변하는지 잰다. 알고리즘 문제는 환경과 무관하게 드러나므로 결과가 그대로 유효하다 |
| 요청량 테스트 | **로컬에서는 예행만** | 부하 스크립트가 제대로 동작하는지 짧게 돌려 확인한다. 수치를 결론으로 쓰지 않는다. 스크립트는 대상 주소, 가상 사용자 수, 폴링 주기, 단계별 증가를 매개변수로 받아 나중에 AWS에서 그대로 쓸 수 있게 만든다 |
| 실제 용량 측정 | AWS(지금은 하지 않는다) | 실제 용량, 대기 트래픽이 예매에 주는 영향, 오토스케일링 반응, 관리형 Redis·DB의 동작. 무엇을 어떤 조건으로 잴지 계획만 문서에 적어 둔다 |

규칙
- 데이터 규모 테스트의 수치도 "이 PC, 이 조건에서의 값"으로 적고, 해석은 인원 증가에 따른 비율과 경향으로 한다. 조건(Redis 버전·설정, 측정 방법, 같은 시간에 돌던 다른 작업)을 함께 적는다.
- 테스트용 Redis와 DB는 개발·통합 테스트용과 분리한다. 끝나면 채워 넣은 데이터를 지운다.
- 스크립트는 `test/load/`, 결과와 해석과 AWS 측정 계획은 `docs/next/load-test.md`에 둔다. 도구는 WSL 배포판 `ticketing` 안에만 설치한다.
- 지금은 AWS 자원을 만들거나 건드리지 않는다. PC 두 대 구성도 준비하지 않는다.
- 시점: 백엔드 2단계(v4)가 끝난 뒤.
